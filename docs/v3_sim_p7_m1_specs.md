## 2. Layout sets (contract §4.1, D8)

**How they were made.** The bound `p5_layouts.generate(seed)` and its unchanged admission filter `rejection()`, in
seed order, plus the P5 split-match exclusion.
* The exclusion uses the 1,650 P5 layouts. The tool regenerates them and stops unless they reproduce the P5 dataset
  manifest and readiness report exactly.
* **Box names:** `p7_box_<k>`, k being the box's position in the generator's list.
* **Declaration label:** every layout's declaration carries `outcome: "p7_not_predeclared"` (D13).
* **Worlds:** each layout's world is generated by the bound `p4_worlds.generate()`, from the PX4 default world the
  P3 manifest pins (`457a363a…`). Its SHA-256 is recorded per layout. The runner (M2) must produce the same world;
  this is a per-flight integrity check.
* **Identity:** the document records the SHA-256 of the 10 generator and configuration files it depends on.

## 3. Schedule (contract §4.2)

**Random stream:**
* `draw(label, i) = int(SHA-256("<layouts canonical SHA-256>:<label>:<i>"))`, big-endian.
* Orders are Fisher–Yates shuffles from the end.
* No seed was chosen by hand: the stream follows from the frozen layouts.

**Pilot (one block, 20 pairs, 40 flights).**
* Each pilot layout is flown twice by each controller, as two pairs in random positions.
* One repeat flies P4 first and the other P5 first, so 10/10 overall. Repeats are numbered in flight order.
* Order: 5000010 (P5 first), 5000013 (P5), 5000016 (P4), 5000001 (P4), 5000008 (P5), 5000013 (P4), 5000001 (P5),
  5000004 (P4), 5000012 (P5), 5000016 (P5), 5000002 (P4), 5000005 (P4), 5000006 (P5), 5000010 (P4), 5000005 (P5),
  5000004 (P5), 5000006 (P4), 5000002 (P5), 5000012 (P4), 5000008 (P4).

**Confirmatory: two pre-registered schedules.**

| Schedule | Pairs | Flights | Blocks | Block sizes |
|---|---:|---:|---:|---|
| 200 | 200 | 400 | 10 | 20 each |
| 250 | 250 | 500 | 13 | 12 × 20, then 10 |

* Each is a random order of the first N layouts in seed order.
* Within every block, exactly half the pairs fly P4 first.
* The pair's two flights run back to back.
* The pilot rule (§4) picks one schedule before the first confirmatory flight. Nothing is added, removed or
  reordered afterwards.

## 4. Analysis plan (contract §5–§7)

[`p7_analysis_plan.yaml`](../simulation/px4_gazebo_p7/configs/p7_analysis_plan.yaml) turns the approved decisions
into exact procedures. These are the choices it fixes that the contract left open, for the operator to confirm:

| Item | Specification | Why |
|---|---|---|
| Primary CI | 95 % Tango score interval for the paired difference | the contract allowed "exact or Tango"; Tango is the standard score interval for paired proportions and behaves well near zero discordance |
| S1 bound | non-inferior if the 2.5th percentile of 10,000 paired-bootstrap means (`default_rng(20261121)`) > −0.05 m | the lower limit of a two-sided 95 % interval, the usual non-inferiority convention (one-sided 2.5 %) |
| S2/S3 test | Wilcoxon signed-rank, zeros dropped; exact if at most 25 non-zero differences and no ties, else normal with tie and continuity corrections; Hodges–Lehmann estimate and Walsh-average CI | fully specified, with no software default left open |
| Fixed sequence | S1 only if the primary rejects, S2 only if S1 passes, S3 only if S2 rejects; otherwise descriptive | D9 |
| Pilot rule | the pilot discordance d over valid pilot pairs; **if d < 27/243 (0.111), the 250-pair schedule, else 200** | makes contract §4.3's "may be raised" deterministic, with the M0 audit's planning value |
| Validity | **valid** = armed evidence: the ULog shows ARMED, or the P2 controller entered TAKEOFF (only reachable after VERIFY_ARMED); if the two disagree, valid plus an integrity event; no armed evidence = infrastructure-invalid | M0 audit §5; C8: never outcome-dependent |
| Missing pairs | excluded and listed; the primary sensitivity counts each as P4 succeeded and P5 failed | contract §6 |
| Unflown pairs | after a stop rule: listed; analysis of completed pairs only if the operator decides | contract §7.3; no interim analysis |
| Safety bounds | zero events in M flights: 1 − 0.05^(1/M); otherwise Clopper–Pearson 95 % | contract §6 |
| Exploratory | adds the order effect (who flew first) and drift across blocks to the contract's list | the schedule balances both, so they can be checked |

**Power at the planning values:** 0.83 at 200 pairs, 0.91 at 250 (M0 audit §4.4). A test recomputes both from
27/243 and 22/27.

## 5. Budget check for the 250-pair schedule

At the measured 1.20–1.27 GB per flight, the pilot and 250 pairs (540 flights) need 650–690 GB. WSL has 840.6 GB
free, so about 150–190 GB would remain. That is just above the 150 GB floor (contract §7.4), which every block
checks before it starts.

If the pilot measures more than about 1.29 GB per flight, the last block of the 250-pair schedule would hit the
floor. It would then need verified copies off the WSL disk under D4, which needs its own authorization. The
200-pair schedule leaves about 290 GB.
